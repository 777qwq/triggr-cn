# 实验分支：屏幕级右滑返回（cn4.17-7）

分支 `exp/screen-swipe`　版本 `1.5.0+cn4.17-7`　基于 `19ecbcf`（cn4.17）

> 这个分支的意义是先验证「屏幕级 HID 注入」这条返回路径通不通，所以在拿到实验结论前
> 不要合并回主线。

## 构建为什么从 -6 才开始能用

`-1` 到 `-5` 全部报废，都是工具链的问题，与实验代码无关：

| 构建 | 产物状态 | 现象 |
|---|---|---|
| `-1` | 旧式 bind 流 | 设置插件 `bad bind opcode 0x00`，打不开 |
| `-2` | 只出 arm64 单切片 | ElleKit 静默跳过，所有触发器失效 |
| `-3` | arm64 代码标成 arm64e | 指针格式对不上，SpringBoard 安全模式 |
| `-5` | 自建 ld64 写出的 arm64e | dyld 能加载，但注入时崩在 `readClass`（`EXC_BAD_ACCESS`，`OBJC_CLASS_$_TGStatusBarHoldTarget`） |

根因是 Linux 上没有能写出 iOS 16 认可 arm64e 类数据的链接器：`ld64.lld` 18/19/20
一律拒绝 arm64e 的 chained fixups；cctools-port 的 `ld64-956.6` 能写出
`pointer_format=12`，但 Objective-C 的签名指针编码和 Apple 的 `ld64` 不一致，
`libobjc` 在 `map_images` 阶段解引用就崩。

`-6` 起改为 **GitHub Actions 的 macos-15 runner** 出包（`.github/workflows/build.yml`），
用 Xcode 自带的 clang + ld64，arm64 / arm64e 双切片一次产出。本地沙盒不再出包。

## 这一版在试什么

「返回上级」不再动视图控制器，改成往触摸子系统注入一次真实触摸：屏幕左缘按下 →
向右拖 10 步（约 200ms）→ 抬起。剩下的交给 App 自己的边缘返回手势，所以走的是原生
转场动画，也不需要猜 App 用的是 nav 还是自绘容器。

## -6 的结论：SpringBoard 里发事件到不了 App

`-6` 在 SpringBoard 进程里用 `IOHIDEventSystemClientCreate` +
`IOHIDEventSystemClientDispatchEvent` 注入，实测日志：

```
注入开始 mode=2 pref=0
页面未变化（mode=2）
```

注入确实执行了（没有符号缺失、没有 client 创建失败），但页面纹丝不动。原因是
`IOHIDEventSystemClientCreate` 建的是 application 类型的 client，dispatch 只在本进程的
HID 事件系统里分发；SpringBoard 自己不是触摸的消费方，真正需要事件的是前台 App，
而触摸跨进程转发走的是 SpringBoard 内部的 mach port 投递（给事件标 contextID 后由
backboardd 转发），不是这条 dispatch 路径。

## -7 改在 App 进程内注入

SpringBoard 只负责递话：`system.back` → `notify_post(TGRelaySwipeGo)`。
Relay 在 App 进程内构造 `IOHIDEvent`，用 `UIApplication` 的私有
`_enqueueHIDEvent:` 直接塞进自己的事件队列，不经过任何 IPC。

因为不能确定事件要不要标窗口 contextID、坐标按归一化还是屏幕点数解释，一次按键按顺序
试五种组合，哪种让页面戳变了就停：

| # | 坐标 | 投递方式 |
|---|---|---|
| 1 | 归一化 | `_enqueueHIDEvent:`（首选） |
| 2 | 屏幕点数 | `_enqueueHIDEvent:` |
| 3 | 归一化 | `_enqueueHIDEvent:` + `BKSHIDEventSetDigitizerInfo(contextID)` |
| 4 | 屏幕点数 | 同上 |
| 5 | 归一化 | `IOHIDEventSystemClientDispatchEvent`（`-6` 的老路，留作对照） |

## 为了排除干扰，摘掉了这些

| 摘除项 | 原因 |
|---|---|
| `system.back` → `notify_post(TGRelayBack)` | 原来的返回入口，不摘就两套机制同时跑 |
| Relay 的 `escape → 公开 pop` 链路 | 同上；代码保留但不再注册通知 |
| Relay 的 `EdgeBack`（强制放行系统边缘返回手势） | 它本身也是一条返回路径，会和注入的滑动抢同一个手势 |

现在按「返回上级」**只有**注入这一条路。注入不生效 = 没反应，没有任何兜底。

## 怎么判断成没成

Relay 在 App 进程里比对页面身份（`TGSwipeStamp`：走 `TGVisibleChain`，把 nav 栈深、
tab 选中项都拼进戳）。每一组注入前取一次戳，手势结束 0.55 秒后再取一次，变了就记为
生效并停止后续组合。

日志：`/var/mobile/Library/Logs/TriggrSwipe.log`

```
tail -f /var/mobile/Library/Logs/TriggrSwipe.log
```

会看到类似：

```
2026-11-07 14:40:02 +0800 注入开始，共 5 组
2026-11-07 14:40:02 +0800 组合 1：归一化 enqueue
2026-11-07 14:40:03 +0800 组合 1 生效，页面已变化
```

## 手动钉死组合

默认五种全跑。已知哪种可用时，钉死能省 3 秒：

```
/var/jb/usr/bin/defaults write com.johndie.triggr SwipeVariant -int 1   # 1..5
```

写完杀掉目标 App 再打开（Relay 跟着 App 进程，重新读配置）。

## 可能的结果与含义

| 日志 | 含义 | 下一步 |
|---|---|---|
| `组合 N 生效，页面已变化` | 注入链路通，N 就是可用配方 | 把该组合设为默认，再做各 App 一致性验证 |
| `所有组合都没让页面动` | 触摸进了事件队列但手势没认 | 检查起点/时长，或该页面确实禁用了返回手势 |
| `取不到窗口 contextID，跳过` | `UIWindow` 私有属性改名 | 组合 3/4 无效，看 1/2 的结果 |
| `IOKit 符号取不到` | 私有符号未导出 | 按系统版本适配 |
| 没有任何日志 | Relay 没收到通知 | SpringBoard 侧通知没发出，或 App 未加载 Relay |
