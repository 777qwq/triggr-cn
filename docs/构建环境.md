# 构建环境（2026-11-07）

这台沙盒以前一直能出包，是因为 `.theos/obj` 里留着更早某个环境（带完整 Apple 工具链）编出来的 arm64e 目标文件，每次只是重新链接。`make clean` + `rm -rf .theos` 之后缓存没了，工具链的真实能力才暴露出来：本机的 `ld64.lld` 根本产不出合法的 arm64e。

## 原作者的说明（`Jond-ie/triggr`，README 的 Building 一节）

> Install from the pwnapple repo unless you want to change the code. You need Theos with an iOS SDK (built against 16.5 from theos/sdks) and the rootless scheme; AltList is vendored in `vendor/` for linking.
>
> ```
> make package FINALPACKAGE=1 THEOS_PACKAGE_SCHEME=rootless
> ```
>
> The Makefile builds arm64. Release builds add arm64e (`ARCHS="arm64 arm64e"`), which needs a clang with the current arm64e ABI (Xcode's, or upstream LLVM 20 or newer).

三条要求逐条对照：

| 作者要求 | 本机情况 |
|---|---|
| Theos + iOS 16.5 SDK + rootless scheme | 有，`/opt/theos`，`iPhoneOS16.5.sdk`，`THEOS_PACKAGE_SCHEME=rootless` |
| 默认 arm64，release 加 `ARCHS="arm64 arm64e"` | 已按此设置 |
| arm64e 需要 Xcode 的 clang 或上游 LLVM 20+ | Xcode 没有；LLVM 20 已装（`clang-20`） |

关键在最后一条。它只说 clang，因为作者在 macOS 上，链接器用的是 Xcode 自带的 `ld64`。**Linux 上链接器不会跟着 clang 一起升级**——这才是这次踩坑的地方。

## 本机的实际组合

| 环节 | 用的是 | 为什么 |
|---|---|---|
| 编译 | `clang-20`（上游 LLVM 20.1.2） | clang-18 编 arm64e 目标文件时 cpusubtype 是旧的 `0x2`；clang-20 输出 `0x80000002`（arm64e + ptrauth ABI） |
| 链接 | 自建 `cctools-port` 的 `ld64-956.6` | lld 不认 arm64e，也不支持 arm64e 的 chained fixups；不加就退回旧式 bind 流，dyld 报 `bad bind opcode 0x00` |
| 框架/库 | `/opt/tgstub` 下的 arm64e 占位库 | 这套 ld64 没编进 libtapi，读不了 SDK 的 `.tbd`；占位库的 `install_name` 与真实框架一致，符号走 `-undefined dynamic_lookup`，运行时从进程已加载的框架解析 |

安装位置：

```
/opt/cctools/bin/ld64                       # cctools-port ld64-956.6
/opt/theos/toolchain/linux/iphone/bin/clang -> /usr/bin/clang-20
/opt/theos/toolchain/linux/iphone/bin/ld    # 包装脚本，转调上面的 ld64，缺什么框架就自动补占位库
/opt/tgstub/                                # 占位库与 _dummy.o
/usr/local/bin/ld -> /opt/theos/toolchain/linux/iphone/bin/ld   # clang 在 Linux 上就调这个名字
```

## ld 包装做了什么

1. `-iphoneos_version_min X` → `-platform_version ios X X`；`-dylib_install_name` → `-install_name`；丢掉 `-mllvm`、`-dynamic`。
2. 统一追加 `-fixup_chains`。
3. 扫 `-framework A` / `-lB`，占位库不存在就用 `_dummy.o` 现场生成一个（`-F` 目录里已有真二进制的跳过，例如 `vendor/AltList.framework`）。
4. 追加 `-F/opt/tgstub/System/Library/{,Private}Frameworks`、`-L/opt/tgstub/usr/lib`，没有显式 `-lSystem` 就补一个 `libSystem.B.dylib` 输入（ld64 强制要求 dylib 链接 libSystem）。

## 产物校验

```
Triggr.dylib  (SpringBoard)  arm64  sub=0x0        ptrfmt=6   链式
                             arm64e sub=0x80000002 ptrfmt=12  链式
TriggrRelay.dylib (App 内)   同上
Triggr (设置插件)            同上
triggr / triggrd             同上
TriggrApp.app                单 arm64（与原版一致）
```

`ptrfmt=12` 是 `DYLD_CHAINED_PTR_ARM64E_USERLAND24`，与能用的 cn4.17 一致。`ptrfmt=6` 是把 arm64 代码标成 arm64e 时会出现的格式，dyld 按 arm64e 解释它就会崩——cn4.17-3 进安全模式就是这个原因。

依赖与签名：

```
LC_LOAD_DYLIB: libobjc, Foundation, CoreFoundation, UIKit, AVFoundation,
               QuartzCore, LocalAuthentication, IOKit, AudioToolbox,
               CallKit, CoreHaptics, libSystem.B
LC_CODE_SIGNATURE: 有（ldid -S）
chained imports: 158 个（cn4.17 是 163 个，差的几个是 libc++ 相关）
```

## 从零重建工具链

```bash
# 1. clang-20
sudo apt-get install -y clang-20 lld-20 libblocksruntime-dev cmake ninja-build

# 2. libdispatch（cctools 依赖）
git clone --depth=1 https://github.com/tpoechtrager/apple-libdispatch.git
cd apple-libdispatch && mkdir build && cd build
CC=clang-18 CXX=clang++-18 cmake -G Ninja -DCMAKE_BUILD_TYPE=Release \
  -DCMAKE_INSTALL_PREFIX=/usr/local -DBUILD_TESTING=OFF -DINSTALL_PRIVATE_HEADERS=YES \
  -DCMAKE_EXE_LINKER_FLAGS=-L/usr/lib/gcc/x86_64-linux-gnu/13 \
  -DCMAKE_SHARED_LINKER_FLAGS=-L/usr/lib/gcc/x86_64-linux-gnu/13 ..
ninja && sudo ninja install

# 3. cctools（ld64）
git clone --depth=1 https://github.com/tpoechtrager/cctools-port.git
cd cctools-port/cctools
./autogen.sh
./configure --prefix=/opt/cctools --target=arm64-apple-darwin \
  --with-llvm-config=/usr/lib/llvm-18/bin/llvm-config CC=clang-18 CXX=clang++-18 \
  LDFLAGS="-L/usr/lib/gcc/x86_64-linux-gnu/13"
make -j$(nproc) CXXFLAGS="-std=gnu++20 -O2 -fblocks \
  -I/usr/include/c++/13 -I/usr/include/x86_64-linux-gnu/c++/13 \
  -I/usr/lib/gcc/x86_64-linux-gnu/13/include -I/usr/local/include"
```

编译期踩到的几个坑，都在上面的参数里：

- `libdispatch` 用 gcc 配置会报 `-fblocks` 不认识 → 必须 `CC=clang-18`；
- clang 探到的是 gcc 14 的头目录（不存在），libstdc++ 又不在默认搜索路径 → 显式 `-I/usr/include/c++/13` 与 `-L/usr/lib/gcc/x86_64-linux-gnu/13`；
- cctools 用 `<span>`，默认不是 C++20 → `-std=gnu++20`。

## 已知代价

占位库方案让所有外部符号走 flat namespace 动态查找（`-undefined dynamic_lookup`），而不是像 `.tbd` 那样记录到具体库的序号。实际影响：

- 框架照样写进 `LC_LOAD_DYLIB`，dyld 会加载它们；
- 符号在加载时从所有已加载镜像里找，SpringBoard / Preferences / App 进程里 UIKit、Foundation 都在，正常；
- 如果某个符号只存在于未加载的框架里，会在加载时报 `Symbol not found` 而不是链接期报错——这是唯一比 `.tbd` 弱的地方。

要彻底回到 `.tbd`，得给 ld64 编进 libtapi（`--with-libtapi`），而 libtapi 依赖 llvm-project 全量源码，这台机器的网络拉不下来（170 MB 的仓库试了两次都 `early EOF`）。相比之下，原作者那条路（macOS + Xcode + GitHub Actions）更省事：仓库里的 `.github/workflows/build.yml` 就是跑在 `macos-15` 上，真 Xcode 工具链，双架构，一次就能出包。
